# Internationalization (i18n) & Localization Guide

This document describes how localization, bidirectional layout (RTL/LTR), route prefixing, and message translation are implemented across the Serag storefront and admin.

---

## 1. Locale Routing & Strategy

Localization is powered by `@nuxtjs/i18n` with the following configuration in `nuxt.config.ts`:

- **Default Locale**: Arabic (`ar`, Egyptian Arabic `ar-EG`, `dir="rtl"`).
- **Secondary Locale**: English (`en`, `en-US`, `dir="ltr"`).
- **Routing Strategy**: `prefix_except_default`.
  - Arabic (default) lives at root paths: `/`, `/shop`, `/admin`, `/admin/login`.
  - English is prefixed: `/en`, `/en/shop`, `/en/admin`, `/en/admin/login`.
- **No browser-language redirect**: `detectBrowserLanguage: false`. `/` is always Arabic (first-time visitors and crawlers included); English is reached only through `/en` links such as the LocaleSwitcher.
- **HTML Attributes**: Direction and language are bound reactively in `apps/web/app/app.vue`:
  ```ts
  const head = useLocaleHead()
  useHead({
    htmlAttrs: {
      lang: () => head.value.htmlAttrs?.lang,
      dir: () => head.value.htmlAttrs?.dir,
    },
  })
  ```

## 2. Locale Message Files & Namespace Schema

Messages are stored as JSON files under `apps/web/i18n/locales/`:
- `apps/web/i18n/locales/ar.json` (Arabic source of truth)
- `apps/web/i18n/locales/en.json` (English counterpart)

### Top-Level Namespaces
Every key must be organized under one of these standardized namespaces:

1. **`brand`**: Core brand identity strings (`name`, `storeName`, `since`).
2. **`common`**: Shared generic UI labels (`mainNav`, `openMenu`, `skipToContent`, `search`, `logout`, `undo`, `showPassword`, `hidePassword`).
3. **`locale`**: Language switching strings (`switch`, `ar`, `en`).
4. **`store`**: Customer storefront labels:
   - `store.header`: Announcement bar, search drawer, navigation links, quick actions.
   - `store.footer`: Contact details, policy links, VAT notice, payment methods, legacy copy.
   - `store.bottomNav`: Mobile bottom navigation labels.
   - `store.home`: Hero subtitles, CTA buttons, sample prices.
5. **`admin`**: Admin portal labels:
   - `admin.nav`: Sidebar navigation groups, overview, orders, products, bridal, settings.
   - `admin.login`: Login card title, subtitle, field labels, side panel feature list, error messages.
   - `admin.dashboard`: Welcome header, performance subtitles, empty states.
   - `admin.topbar`: Portal header, shortcut tooltips, user menu.
   - `admin.shortcuts`: Keyboard shortcuts modal titles, chord instructions.
   - `admin.commandPalette`: Command palette search placeholder, command lists, theme toggle.
6. **`validation`**: Client-side form field validation messages (`emailRequired`, `emailInvalid`, `passwordRequired`).
7. **`errors`**: General system failure messages (`generic`).

## 3. The Strict Parity Rule (`i18n-messages.test.ts`)

Every time a string is added, modified, or removed, **both** `ar.json` and `en.json` must be updated in the exact same commit.

The unit test `apps/web/test/i18n-messages.test.ts` runs automatically during `pnpm test` and CI:
- **Rule 1**: The flattened key set of `ar.json` and `en.json` must be identical (`arKeys.toEqual(enKeys)`).
- **Rule 2**: No empty strings are allowed in either file (`value.trim() !== ''`).
- **Failure Consequence**: Any missing key or untranslated blank string breaks the test suite immediately and fails the PR gate.

```json
// Example: Adding a new confirmation action
// ar.json
{
  "admin": {
    "orders": {
      "confirmPayment": "تأكيد الدفع"
    }
  }
}

// en.json (must match exact key path)
{
  "admin": {
    "orders": {
      "confirmPayment": "Confirm Payment"
    }
  }
}
```

## 4. Navigation & Internal Links: Always Use `localePath()`

Never hardcode localized paths in templates or router calls. Always wrap paths with `localePath()`.

### Why?
Hardcoding `<NuxtLink to="/admin">` in English context (`/en/...`) breaks navigation by stripping the locale prefix and dropping the user back to the default Arabic locale.

```vue
<!-- ❌ BAD: Hardcoded path strips locale prefix in English -->
<NuxtLink to="/admin/orders">
  {{ t('admin.nav.orders') }}
</NuxtLink>

<!-- ✅ GOOD: Automatically resolves to /admin/orders (ar) or /en/admin/orders (en) -->
<NuxtLink :to="localePath('/admin/orders')">
  {{ t('admin.nav.orders') }}
</NuxtLink>
```

In script setup:
```ts
const localePath = useLocalePath()
await navigateTo(localePath('/admin/login'))
```

## 5. Constants Store Keys, Translate at Render

Never store translated strings in static arrays, objects, or constants.

- **Rule**: Constants in `app/constants/` must hold the translation key string (e.g. `labelKey: 'admin.nav.orders'`).
- **Translation**: Call `t(item.labelKey)` inside the Vue template or computed property at render time.

```ts
// app/constants/navigation.ts
export interface AdminNavShortcut {
  key: string
  labelKey: string
  to: string
}

export const ADMIN_NAV_SHORTCUTS: readonly AdminNavShortcut[] = [
  { key: 'o', labelKey: 'admin.nav.orders', to: '/admin/orders' },
  { key: 'p', labelKey: 'admin.nav.products', to: '/admin/products' },
] as const
```

In the template:
```vue
<span v-for="item in ADMIN_NAV_SHORTCUTS" :key="item.to">
  {{ t(item.labelKey) }}
</span>
```

## 6. Path Comparisons: Use `stripLocalePrefix`

When checking whether the current URL matches a route prefix (e.g. in middleware, active link highlighting, or redirect validation), always strip the `/en` prefix first.

Use `stripLocalePrefix` from `app/utils/i18n.ts`:

```ts
// app/utils/i18n.ts
export function stripLocalePrefix(path: string): string {
  const stripped = path.replace(/^\/en(?=\/|$)/, '')
  return stripped === '' ? '/' : stripped
}

// In redirect resolver (app/utils/auth.ts):
const base = stripLocalePrefix(pathname)
if (/^\/admin(\/|$)/.test(base) && !/^\/admin\/login(\/|$)/.test(base)) {
  return raw
}
```

## 7. Never Show Raw Server Errors: Map Status → i18n Key

Backend error strings must **never** be rendered directly in the user interface.
- Raw server error strings may leak internal stack traces or database errors.
- Raw server messages cannot be localized reactively.

### The Mapping Pattern
Use utility mappers (such as `loginErrorKey` in `app/utils/auth.ts`) to map HTTP response status codes or error codes to i18n keys:

```ts
// app/utils/auth.ts
export function loginErrorKey(err: unknown): string {
  const status = getErrorStatus(err)
  if (status === 400 || status === 401) {
    return 'admin.login.errors.invalidCredentials'
  }
  if (status === 429) {
    return 'admin.login.errors.tooManyAttempts'
  }
  return 'errors.generic'
}
```

In the component/composable:
```ts
try {
  await login(email, password)
} catch (err: unknown) {
  formError.value = t(loginErrorKey(err))
}
```

## 8. Language Switcher (`CommonLocaleSwitcher`)

Language switching is handled by `components/common/LocaleSwitcher.vue` (auto-imported as `<CommonLocaleSwitcher>`):
- Uses `useSwitchLocalePath()` to preserve the current route while flipping the locale segment.
- Marks the link with `:lang="other.code"` and `:hreflang="other.language"`.
- Supports `'default'` or `'pill'` visual variants.

```vue
<!-- Example usage in topbar or login header -->
<CommonLocaleSwitcher variant="pill" />
```

## 9. Typography & Fonts Per Locale

Fonts are configured via `@nuxt/fonts` in `nuxt.config.ts`:

| Font Family | Subsets | Usage |
|---|---|---|
| **IBM Plex Sans Arabic** | `arabic`, `latin` | Primary Arabic body copy and clean user interface text. |
| **Lalezar** | `arabic`, `latin` | Arabic display headings, brand names, and banner titles (`font-display`). |
| **Outfit** | `latin` | English headings, Latin text, and numeric tags (`.num`). |
